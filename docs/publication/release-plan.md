# Website release plan

The stages, gates, and rollback procedure for publishing the Outcome Engineering methodology at outcome.engineering. The methodology repository settles and exports the method; this repository renders and deploys it.

Stage S1 waits on the methodology repository's export milestone. S2 additionally waits on its public manuscript. S0 needs neither and can begin from this plan.

## Website implementation

### S0: Establish the website foundation with fixtures

**Purpose**

Prepare the website application and verification contract without depending on unsettled methodology prose or the unfinished publication exporter.

**First action after session transfer**

1. Inspect all website worktrees, branches, remote refs, and local modifications.
2. Preserve the modified `refactor/xiperlabs-architecture` checkout.
3. Create a fresh publication worktree from current `origin/main` or another operator-selected base.
4. Read this proposal and verify every dated deployment observation.
5. Inspect current Vercel project linkage, environment variables, DNS, and preview behavior without changing production.

**Outputs**

- fresh isolated worktree and current-state inventory;
- the required package scripts, Playwright and axe dependencies, and blocking CI jobs named in site architecture;
- closed content and authority types;
- `fixtures/publication/`, containing a fixed fixture manifest and representative positioning, guide, example, reference, and knowledge pages, a versioned diagram specification, methodology redirect cases, complete source provenance, indexability metadata, and valid digests;
- website-owned tool and editorial fixtures with their family metadata, plus a host-aware legacy-redirect fixture covering same-origin and cross-origin destinations;
- `publication.fixture.lock.json`, carrying the fixture manifest and artifact digests and an explicit `source_kind: fixture` marker;
- `content:sync:fixture` and `content:check:fixture` commands;
- typed manifest loader and family-specific metadata validation against fixtures;
- publication layouts, provenance labels, version labels, and route fixtures;
- legacy URL inventory;
- no replacement of canonical homepage claims or production routes.

**Done when**

The content pipeline has one validation-and-materialization core that accepts an already obtained artifact directory. During S0, `content:sync:fixture` copies the committed fixture into a temporary generated directory, `content:check:fixture` compares that result and both fixture-lock digests with the committed fixture projection, and `pnpm verify` invokes `content:check:fixture` before repository validation, types, lint, tests, production build, links, end-to-end behavior, and automated accessibility. Marketing, Method, Example, Reference, Knowledge, Tool, and Editorial layouts render their named fixture content; the merged route inventory, preview indexability, and both redirect classes pass their contract tests; and the current production homepage remains unchanged.

### S1: Integrate the pinned publication export

**Purpose**

Replace the fixture boundary with one pinned, verified methodology publication artifact after M6 reaches the methodology default branch.

**Outputs**

- `content/methodology/locks/next.lock.json` pinned to the full methodology commit;
- `content/methodology/projections/next/`;
- `content:sync` and `content:check` implementations using the real exporter;
- manifest and artifact digest verification;
- generated route inventory;
- one rendered method page and one reference page proving provenance, content type, authority, version, and digest labels;
- CI rejection of source drift and manual generated-content edits.

**Done when**

A methodology pin update produces a complete reviewable content diff, every generated byte and route verifies against the lock, and the fixture adapter has been removed from production code.

S1 keeps the shared artifact validator and materializer. It adds a pinned-repository acquisition adapter, replaces the fixture lock with `content/methodology/locks/next.lock.json`, points `pnpm verify` at `content:check`, and removes `source_kind: fixture` handling plus fixture-copy selection from production commands. Fixture files remain test inputs for parser and failure-case tests; no production route or synchronization command can select them.

### S2: Build the replacement homepage and publish the method-guide preview

**Purpose**

Make the complete new argument reviewable under versioned `next` routes while the production root continues to represent the current canonical release.

**Outputs**

- homepage sections from the exposition;
- program-logic diagram;
- continuous-reconciliation diagram;
- authority-and-learning diagram;
- human-agent boundary;
- three-perspective projection;
- Change-lineage preview;
- method-guide pages;
- accessible worked example;
- `/method/next/overview` as the exact replacement-homepage preview;
- no mutation of `/`, moving release aliases, or the current-release pointer.

**Done when**

The versioned preview contains no obsolete current-method claim, every diagram has a text equivalent, the method guide passes comprehension review, and `/` remains bound to the current canonical release.

### S3: Publish reference, knowledge, and tools

**Purpose**

Complete progressive disclosure from argument to rule and operation.

**Outputs**

- generated normative reference;
- knowledge index and selected entries;
- source and influence page;
- tool entry points;
- migration glossary;
- version selector or preview label;
- source links for every imported page.

**Done when**

A reader can move from any explanatory claim to its governing reference and from any knowledge entry to the rule that graduated from it.

### S4: Migrate and release

**Purpose**

Retire obsolete public claims safely and cut over production.

**Outputs**

- legacy URL inventory;
- host-aware `redirects/legacy-routes.json` and its digest;
- immutable full-version lock and generated projection retained beside all prior releases;
- `content/methodology/current.json` selecting the new full release;
- atomic activation of `/`, moving aliases, sitemap priority, and search ranking from that pointer;
- redirects and historical pages;
- removal or archival of obsolete hard-coded story data;
- Mintlify retirement or tool-only boundary;
- canonical metadata and sitemap;
- production deployment;
- post-deployment smoke evidence;
- approved human accessibility evidence under `docs/release-evidence/accessibility/`;
- release announcement linked to the methodology version and source commit.

**Done when**

All publication gates pass, production serves the approved source digest, important legacy links resolve intentionally, and rollback remains possible.

## Review

Review source provenance, generated-content integrity, rendering, accessibility, responsive behavior, interaction, performance, metadata, and deployment separately. Visual approval does not substitute for conceptual approval.

## Rollback

Before cutover, create the four versioned evidence files defined under [rollback evidence schemas](site-architecture.md#rollback-evidence-schemas). The rollback record identifies the prior Vercel deployment and external-documentation deployment, covers the authoritative DNS configuration and redirect inventory, and records the new approved publication digests.

The prior-site route snapshot covers every route in the prior sitemap, every route reached by crawling internal links from `/`, and every changed legacy URL. The external-documentation snapshot covers every entry point and changed documentation URL. These snapshots supply the required legacy evidence when the prior deployment exposes no methodology or artifact digest.

Keep the prior Vercel deployment and external documentation snapshot deployable for fourteen calendar days after cutover. Keep retired content and redirect configuration versioned and recoverable throughout the same window; deletion occurs only after the window closes and the operator approves disposal.

A rollback restores the prior Vercel deployment, the prior DNS targets when cutover changed DNS, the prior redirect map, and the previous external-documentation deployment or historical routes. After DNS propagation, regenerate every component through the same versioned schemas and require all component digests and `prior_state_sha256` to equal the recorded values. Record the restored deployment identities and comparison result.

Content rollback and methodology rollback are separate decisions. A site defect can roll back presentation without withdrawing an already released methodology version. A conceptual defect requires a new methodology correction and publication pin, preserving source history.

## Changeset sequence

Work begins with S0 after verifying repository, worktree, remote, deployment, and DNS state. S0 is limited to application infrastructure and fixture-backed behavior:

- fresh worktree creation;
- current-site inventory;
- package scripts, dependencies, and blocking CI configuration;
- complete route and component scaffolding using fixtures;
- content-manifest loader using fixtures;
- provenance and authority components;
- quality-gate setup;
- legacy URL inventory.

Once the methodology repository's export milestone reaches its default branch, S1 replaces fixtures with the exact pinned export and establishes generated-content integrity. S2 begins only when S1 and the methodology repository's public manuscript are both complete, and publishes the new experience solely under `next` routes. S4 creates and retains the immutable full-version projection, changes the current-release pointer, and activates `/` plus moving aliases in the production cutover.

The first website changeset contains S0 only: verification commands, CI gates, typed schemas, fixture loader, page-family shell, and legacy inventory. The second contains S1 only: the `next` methodology lock, real export synchronization, generated content, digest verification, and representative rendered pages. S2 completes the versioned preview. The production homepage changes only during S4's atomic promotion after the full release artifact is retained and approved.
